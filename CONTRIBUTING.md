# Contributing

Thanks for helping. Issues and pull requests are welcome.

## Layout

| Path | What lives there |
| --- | --- |
| `schema/` | The shared data model (JSON Schema) |
| `tools/schemagen` | Generates `internal/model` and `frontend/src/model/model.gen.ts` from the schema |
| `tools/synthrepo` | Generates large repositories for performance testing |
| `internal/gitexec` | Runs git: tracing, cancellation, serialized writes |
| `internal/repo` | Parses git output into entities |
| `internal/graph` | History loading, lane layout and row windows |
| `internal/watch` | Filesystem watching, coalesced into refresh requests |
| `internal/synchub` | Snapshots and sequenced deltas sent to the frontend |
| `internal/workspace` | Open repositories, refreshes, checkout and worktree commands |
| `internal/prefs` | Preferences and session files |
| `internal/telemetry` | OpenTelemetry setup and frontend span ingest |
| `internal/rpc` | Wails-bound services |
| `internal/perf` | End-to-end performance budgets |
| `frontend/src/services` | Effect services: Rpc, SyncClient, GraphData, Commands, Preferences, Telemetry |
| `frontend/src/data` | TanStack DB collections mirroring backend channels |
| `frontend/src/components` | React UI |

## Everyday commands

```sh
wails dev                                   # run the app with hot reload
go test -race ./internal/... ./tools/...    # backend tests
cd frontend && bun run typecheck && bun run test
```

`wails dev` also serves the app at http://localhost:34115, where a normal browser can call the Go backend. That is handy for browser devtools.

## Changing the data model

Edit `schema/forkit.schema.json`, then regenerate:

```sh
go generate ./schema
```

CI fails if the generated files are out of date. Wails bindings in `frontend/src/wailsjs` are regenerated by `wails dev`, `wails build` or `wails generate module`, and are checked the same way.

## Performance

The budgets are 300 ms from opening a repository to its first graph window, 100 ms from a change on disk to the UI updating, 50 ms to switch emphasis, and 150 MB of memory per repository. `internal/perf` checks them end to end against a real repository.

Repositories big enough to matter are too large to commit, so generate them locally:

```sh
go run ./tools/synthrepo -profile busy-branches -out ~/forkit-perf/busy
go run ./tools/synthrepo -profile deep-history -out ~/forkit-perf/deep    # slower; over a million commits

FORKIT_PERF_REPO=~/forkit-perf/busy/repo go test ./internal/perf -v -count=1
```

- `busy-branches` reproduces a squash-merge workflow: thousands of left-over remote branches, frequent release tags, a wide graph and a large pack. Repositories like this are slow to open in many clients.
- `deep-history` stresses history walking and layout.

Each profile produces a bare `origin.git` and a `repo` clone, so fetches work against it. The test logs a span breakdown of any slow step. Any local repository works as `FORKIT_PERF_REPO` too.

## Tracing

Traces go to `traces.jsonl` in Forkit's cache directory by default. To browse them in Jaeger:

```sh
docker compose -f dev/compose.yaml up -d
FORKIT_OTLP_ENDPOINT=http://localhost:4318/v1/traces wails dev
```

Then open http://localhost:16686. Frontend and backend spans share traces, so you can follow a click through the RPC to the git processes it ran.

## Code style

- Keep code small and obvious. Prefer names and types that make comments unnecessary, and write comments only for what the code can't say: why, constraints, surprises.
- Frontend side effects go through Effect services. Check Effect v4 APIs against the installed `effect` package and its `ai-docs`; don't rely on memory.
- Never render repository content (commit messages, branch names, file contents) as HTML.

## Commits and releases

Use [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `test:`, `chore:`). release-please turns them into the changelog and version tags when changes reach `main`.
